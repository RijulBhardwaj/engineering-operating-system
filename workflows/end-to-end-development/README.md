# End-to-End Development Pipeline (master index)

Single pipeline assembled from this harness's existing rules, stage by stage, with explicit artifacts passed between stages, named loop-back edges, and a parallel dispatch model. It is not claimed to be an exhaustive enumeration of every rule file in this repo -- see each rule file itself for anything not surfaced here. This file is the map; each stage's actual rule/workflow doc stays the source of truth for its own detail -- don't duplicate their content here.

Adopted 2026-11-24 per explicit user instruction ("create the entire workflow layers and loops and passing context and loop back for end to end development... easily modifiable based on the project idea... go deep... bake it in everywhere"). **Revision 6**, after five goldfish reviews. Rev 1-4 were rejected outright; Rev 5 was **approved with minor revisions** (a loose layer citation, an unflagged policy-vs-configuration conflict on secret scanning, a task-identity loophole in the circuit breaker, and the branch-protection section leading with the aspiration instead of the gap) -- all fixed here in Rev 6. Full history in `knowledge/log.md`. Not every gap is closed by this doc alone -- see each section's explicit "residual risk"/"convention only"/"flagged, not silently resolved" callouts below for what is still unenforced or in conflict with another policy file.

## Project profile (makes this modifiable per project idea)

Every project declares a profile in its own `projects/<name>` registry entry (or a project-local `PROFILE.md` if none exists yet). Each field maps to a concrete mechanism already in this harness -- not a new unenforced flag:

```yaml
size: weekend | small | medium | large   # scales DEPTH of stages 1-2 (how many spec docs, how long the design doc) -- per architecture.md's existing "scaled to project size" rule. Does NOT skip Gate 0: only architecture.md's own trivial-change exception (typo/one-line/mechanical rename) skips Gate 0, regardless of size.
risk: low | elevated | regulated         # regulated adds the matching domain reviewer to stage 9 (e.g. healthcare-cdss-patterns/HIPAA skills for health data, security-bounty-hunter for high-value targets) and requires an explicit compliance line in the ADR (stage 4)
ui: none | basic | rich                  # rich means ui-ux-states.md's 44-state checklist is part of stage 7's edge-case tests (ai-code-qa-gate.md layer 2); none means that layer skips UI states entirely, nothing else changes
team: solo-agent | multi-agent           # affects ONLY whether stage 6's leaf tasks dispatch as parallel Agent calls (multi-agent) or run sequentially in the one orchestrating session (solo-agent). It does NOT touch stages 3 or 8: the goldfish (stage 3) is always a fresh subagent with no shared memory, and Review Council (stage 8) is always a separate dispatch from whichever session/agent wrote the code, in both modes -- those two requirements are structural, not a parallelism choice.
```

A `weekend`/`low`/`none` project still walks every stage -- Gate 0 included -- just with a one-paragraph design doc and a lighter stage-9 pass instead of a 12-page spec and a compliance review. This is the actual lever: depth and which specialist joins stage 9, not which stages exist.

**Schema location (so something actually reads this, not just prose):** add a `profile:` block with these four keys directly under the project's entry in `projects/project-registry.yaml`:
```yaml
  - name: my-project
    status: active
    profile: { size: medium, risk: low, ui: rich, team: multi-agent }
```
Any session working the project reads this block at session start (`CLAUDE.md`'s session-start checklist already says "check project-registry.yaml for this project's entry") and applies the scaling described above from there. **Current enforcement is this convention only -- no automated validator or lint check reads/enforces this schema yet.** It lives in the one file every session already reads first, which is a real step up from an unlocated convention, but it is not yet mechanically checked; that gap is a legitimate candidate for the self-optimization loop to propose fixing (e.g. a lint check that flags a registry entry missing a `profile:` block).

## No agent spawns agents (hard platform constraint -- read before the stages below)

The standing platform rule is: agents never spawn agents. There is no real two-level agent hierarchy available here, so this pipeline does not pretend otherwise. **The orchestrator is always the one session** (this session, or a session you explicitly started for the purpose) -- never a dispatched subagent. What "multiple orchestrator subagents" becomes concretely, within the actual constraint:

- The orchestrating session can manage several independent **streams** (frontend/backend/infra, etc.) concurrently -- one batched `Agent` dispatch per stream, all streams' batches issued together when they don't share files, not serialized one stream at a time.
- A "stream" is a planning grouping the orchestrator uses, not a separate agent that itself dispatches agents. The orchestrator defines each stream's interface contract (API shape, shared types, file boundaries) before dispatching, then dispatches every leaf specialist agent directly, batched by stream.
- If a task genuinely needs multi-level delegation at real session scale (not a subagent), that's a `mcp__ccd_session__start_session` call -- a separate Claude Code session is not a "spawned agent" under this rule and can run its own orchestration loop independently, with its own evidence reported back. Reach for this only when the work is large enough to deserve its own session (per that tool's own guidance), not as a workaround to fake agent-spawns-agent.

All named roles below (`software-architect`, `security-engineer`, `devops-engineer`, `code-reviewer`, `quality-gatekeeper`, `failure-recovery`) are real personas in `.claude/agents/` -- dispatch them as that persona's contract specifies, not as a literal `subagent_type` string. `engineering-skills:adversarial-reviewer` is a skill, not an agent type: the fresh verifier subagent (stage 8, item 3 below) is dispatched as a general-purpose agent instructed to follow that skill's methodology, same pattern as any other skill-driven subagent.

## Stages, artifacts, and where each lives

| # | Stage | Owns | Input artifact | Output artifact | Detail lives in |
|---|---|---|---|---|---|
| 1 | Idea / requirements | user + orchestrating session | user request | requirements doc (scaled by profile) | `architecture.md` Spec-driven |
| 2 | Plan (Elephant) | orchestrating session | requirements doc | design doc + acceptance criteria (problem, approach, alternatives, risks) | `architecture.md` Gate 0, Gate 3 |
| 3 | Plan review (Goldfish) | fresh memoryless subagent | design doc alone, no chat history | approve / revise+reasons / reject+reasons | `architecture.md` Gate 0 |
| 4 | Architecture + ADR | software-architect agent | approved design doc | ADR (Accepted), compliance line if `risk: regulated` | `architecture.md` Architecture-first, ADRs |
| 5 | Task decomposition | orchestrating session | ADR + design doc | task graph (owner, files, dependency edges, per-task acceptance criteria, stream grouping) | `agent-coordination.md` Orchestrator |
| 6 | Parallel implementation | orchestrating session dispatches specialist agents, batched per stream | task graph | diffs + per-task evidence | `agent-coordination.md` |
| 7 | AI Code QA Gate (mechanical layers) | implementing agent runs its own static/unit/integration/mutation tools | diffs | tool output (pass/fail, not a verdict) | `ai-code-qa-gate.md` layers 1,2,3,5 |
| 8 | Review Council (= QA Gate layer 4, peer review) | parallel domain reviewers + adversarial verifier + quality-gatekeeper, never the implementing agent/session | diffs + stage 7 tool output | ranked findings (CONFIRMED/PLAUSIBLE), gate pass/fail | Review Council (below); `ai-code-qa-gate.md` layer 4 |
| 9 | Infra/compliance/perf validation | security-engineer + risk-matched specialist | reviewed diffs | infra/secret-scan results, perf budget check, compliance line signed off | `security.md`, `system-design-patterns.md` |
| 10 | Merge, deploy + verify | devops-engineer | passing stages 7-9 | `SETUP_AND_RUN.md` filled in (per `templates/setup-and-run/setup-and-run-template.md`), live verification, merged PR | `architecture.md` Gate 6 |
| 11 | Monitor + feedback | runtime monitoring (`ai-code-qa-gate.md` layer 5) | production signal | incident report, or a requirements gap if the running system reveals one | `workflows/deployment/` |
| 12 | Self-optimization | orchestrating session, periodic, human-approved | accumulated lessons/logs | rule/registry diffs via PR | Self-optimization loop (below) |

Stage 7 being run by the implementing agent is not an exception to `agent-coordination.md`'s "no agent approves its own work" -- the agent runs the *tool* and reports its objective output (a test either passed or didn't; that's the tool's verdict, not the agent's), which is exactly what that rule means by "automated, not self-attested." The agent cannot decide the output means something other than what the tool printed. The actual review *verdict* (does this diff merit merging) always sits at stage 8, a separate dispatch.

One owner per security tool, no duplicate runs: Semgrep, Bandit, and the dependency audits (`npm audit`/`pip-audit`) are rows in `ai-code-qa-gate.md`'s tool-stack table under that file's layer 1, static analysis -- that file doesn't itself number them "layer 1," this doc is the one making that mapping explicit. They run once, in stage 7, per change; stage 9 does not re-run them. Stage 8's `ecc:security-reviewer` reads stage 7's Semgrep/Bandit *output* plus the diff itself for logic/auth issues those tools can't catch (business-logic authz, prompt-injection-shaped input handling) -- it does not re-scan.

Stage 9 owns what stage 7 structurally can't produce from a diff alone -- and this harness does not yet have every tool that implies installed, which this doc states rather than hides: full-repo/history **secret scanning** (candidate tool: `gitleaks`, not yet registered in `registry/tools.yaml` -- install it the first time a project actually reaches stage 9, per `policies/skill-installation-policy.md`, not speculatively now); **infra/deployment config review** (Dockerfiles, IaC, CI config; candidate: `checkov` or `tfsec` depending on the project's IaC tool, same install-on-first-need rule); **perf budget check** (no single harness-wide tool -- the specific tool, e.g. `k6`/`lighthouse`/`autocannon`, is chosen per project at stage 4 based on what's actually being built, and that choice is recorded in the ADR); and the **compliance sign-off** (a human-readable statement against the `risk: regulated` requirement, not a scan).

**Flagged, not silently resolved**: `security.md` states "Pre-commit/CI secret scanning on every repo bootstrapped from this system" as a standing policy, while no secret scanner is actually registered in `registry/tools.yaml` today -- policy and current harness state disagree. Per `CLAUDE.md`'s own precedence rule (a conflict gets flagged, not picked silently), this doc does not resolve it: either `security.md`'s claim needs to become true (install `gitleaks` and wire a pre-commit/CI hook project-wide) or the claim needs correcting to describe what's actually enforced today. Candidate self-optimization item.

## Loop-back table (where a defect returns to, never patched at the wrong layer)

| Defect found at... | Returns to... | Not to... |
|---|---|---|
| Goldfish review (stage 3) rejects | Elephant redrafts (stage 2), new goldfish | Proceeding to architecture anyway |
| Architecture/ADR review finds the plan unworkable | Plan (stage 2) | Patching the ADR around a bad plan |
| Task decomposition (stage 5) produces overlapping file ownership or an infeasible dependency graph | Re-decompose at stage 5 with corrected boundaries, or Architecture (stage 4) if the ADR itself forces the conflict | Letting two tasks write the same file and resolving it after the fact |
| Implementation (stage 6) or QA Gate (stage 7) discovers the *plan itself* is wrong, not just the code | Plan (stage 2): new design doc, new goldfish review (stage 3) | Coding around a bad plan to make tests pass |
| QA Gate (stage 7) tool output fails | Implementation (stage 6), same task, evidence attached | Loosening the gate's checklist |
| Review Council (stage 8) finds a logic/security bug | Implementation (stage 6) | The reviewer fixing it inline in the same pass it found it (no self-approval) |
| Review Council finds an ADR violation | Architecture (stage 4): supersede the ADR explicitly, or implementation conforms to it | Silent drift either direction |
| Infra/compliance/perf validation (stage 9) fails | Implementation (stage 6), or Architecture (stage 4) if the architecture itself can't meet the budget | Merging with a known failing scan |
| Deploy/verify (stage 10) fails | Implementation (stage 6) | Shipping anyway and monitoring for it |
| Production incident (stage 11) | Root-caused via `failure-recovery.md`, fix re-enters at stage 6, lesson files into `knowledge/wiki/` | A silent hotfix with no lesson captured |
| Monitoring (stage 11) reveals the original requirement was wrong, not just the implementation | Requirements (stage 1): new requirements doc | Patching production behavior without updating what was actually asked for |
| Plan review (stage 2/3) or infra/compliance validation (stage 9) reveals the requirement itself was never viable (e.g. a regulated-data requirement that can't actually be met) | Requirements (stage 1): new requirements doc, scoped to what's actually viable | Forcing a plan or implementation to satisfy an unviable requirement |
| Same failure mode recurs across projects | Self-optimization (stage 12) updates the shared rule, not just the one project | Each project independently rediscovering the same fix |

## Context passing (why re-derivation stays cheap)

Every stage writes its output artifact to disk (not just chat) before the next stage starts -- the design doc, the ADR, the task graph, the review findings, the checkpoint. A later stage (or a resumed session) reads the artifact, never re-derives it from conversation history. **This is convention, enforced by discipline, not by a mechanical check** -- nothing currently blocks a stage from proceeding without having written its artifact; same caveat as the profile schema above. This is `token-efficiency.md` and `knowledge-wiki-ops.md`'s rule applied structurally: the pipeline itself is the context-passing mechanism, not a side effect of remembering to write things down.

**Where these actually live** (so "written to disk" isn't itself vague): design doc and ADR go in the project's own `docs/` tree (`docs/PRD.md`, `docs/architecture/decisions/`, per `workflows/project-initialization/README.md`'s file structure); the task graph and per-task evidence go in `observability/progress/` as a checkpoint, per this harness's existing session-resume convention; Review Council findings and the stage 9 scan output are whatever the PR itself carries (diff + CI output) plus a note in `observability/progress/` if the task spans more than one session.

## Review Council (stacked checks, explicitly not a 100%-guarantee)

No review process catches every defect, and this one has a specific, acknowledged correlation risk: every reviewer here is an instance of the same underlying model family, so a blind spot common to that family (not role-specific bias) can slip past all of them at once. Stacking independent *roles* catches what one role structurally can't (a security reviewer misses a naming/duplication issue a domain reviewer catches, and vice versa) -- it does not fully substitute for a genuinely different reasoning system or a human reviewer on consequential changes.

1. **Scope detection**: identify changed file types/domains (per `registry/SKILL_CLASSIFICATION.md`).
2. **Parallel domain reviewers**: the orchestrating session dispatches the matching language/framework reviewer(s) (e.g. `ecc:python-reviewer`, `ecc:react-reviewer`, `ecc:go-reviewer` -- whichever match) plus `ecc:security-reviewer` and `.claude/agents/code-reviewer.md`, all in the same batch, all read-only against the diff, none of them the agent/session that wrote the code.
3. **Adversarial verification**: every CONFIRMED-severity finding goes to a fresh verifier subagent (`engineering-skills:adversarial-reviewer` or `/code-review`'s own verify pass) with no memory of who raised it, to either confirm or downgrade to PLAUSIBLE.
4. **PLAUSIBLE disposition**: a PLAUSIBLE finding is not silently dropped -- it's reported alongside CONFIRMED findings, and `quality-gatekeeper.md` (or a human, for anything consequential) decides whether it blocks merge. Only CONFIRMED findings are mandatory-fix; PLAUSIBLE findings must still be visible in the final report.
5. **Gatekeeper pass**: `quality-gatekeeper.md` checks the lifecycle gates are actually satisfied (evidence, not assurance) -- distinct from code-level correctness.
6. **Residual-risk statement**: the council's output always includes what it did *not* check (e.g. "no runtime/load test performed," "no manual accessibility audit," "all reviewers share a model family") -- an unstated gap is worse than an acknowledged one.

This is not a substitute for human sign-off on consequential/irreversible decisions (`architecture.md` Gates, final line).

## Self-optimization loop

The harness reviews itself, not just the projects running through it -- bounded tightly, because this loop editing its own guardrails unsupervised is the one failure mode that could silently erode everything else in this pipeline.

1. **Trigger**: after a project reaches a milestone (Gate 6 passes), after a production incident is root-caused, or on explicit user request ("audit the harness").
2. **Input**: `knowledge/log.md` entries since the last pass, `observability/progress/` checkpoints, any `registry/*.yaml` entries whose `last_reviewed` predates the current lessons.
3. **Action**: same as `knowledge-wiki-ops.md`'s Lint operation, targeted at the harness's own rules/registries -- a rule silently worked around twice, a registry `decision` field a recent lesson contradicts, or a pipeline gap.
4. **Hard-excluded from self-edit, no exception**: the entire `.claude/` directory (every rule, every agent persona, every hook/skill config), `policies/`, `CLAUDE.md` itself, and this file (`workflows/end-to-end-development/README.md`). That is everything this pipeline's own rigor depends on -- if it's reachable from this loop, it isn't actually a guardrail. A lesson that implies one of these needs to change produces a *proposal* (written to `observability/progress/` or the PR description), never a direct diff to the file itself. Changing anything in this excluded set is itself a Gate-0-worthy decision -- it goes through the full pipeline (stages 1-4), not through this loop. This narrows (not contradicts) `knowledge-wiki-ops.md`'s Lint "fix on sight" rule: Lint still fixes project docs/wiki pages on sight as that rule says; when Lint's target falls in this excluded set, it proposes instead, per this rule.
5. **Output for everything else** (registries under `registry/`, project-level docs, non-excluded workflow stubs): a branch + PR against this repo proposing the specific diff, with the triggering evidence cited -- never a silent self-edit.
6. **Approval, led with the actual gap, not the aspiration**: this repo's current `main` branch protection does **not** technically require any human approval before a PR merges (`required_approving_review_count: 0`, read via `gh api repos/.../branches/main/protection` this session) -- every PR this session, including earlier ones in this same conversation, was in fact opened and merged by this session alone, no separate review step. **Flagged, not silently resolved**: `policies/branch-protection.md` itself documents a stricter policy than what's configured -- "require 1 review (self-review acceptable for a solo repo, but the review step... is not skippable)" and "require status checks to pass." The written policy already permits self-review; it still requires *a* review step to actually happen. The configured setting (0) doesn't force even that. This is a policy-vs.-configuration conflict, same category `CLAUDE.md` says to flag rather than pick a side of: either tighten the GitHub setting to match the written policy, or correct the policy doc to describe what's actually enforced. This doc does neither unilaterally. What direct-push protection *does* verifiably do: a direct `git push` to `main` earlier this session was rejected with GitHub's own error GH006, in this session's own command output -- that much is real and current. Given the gap above, the self-optimization loop's actual safeguard is procedural, not structural: this session (and any future one) does not call `gh pr merge` on a PR it labels as a self-optimization change -- it opens the PR and stops, leaving the merge action to the user.

## Circuit breakers (bounded failure, matching the platform's existing rule exactly)

Same thresholds as the platform's own autonomous-execution rule, stated without adding a reset condition that would defeat it: a failing command/approach is never repeated identically. 1st failure: capture the error, find root cause, apply a corrected fix, rerun. 2nd failure (the corrected rerun also fails): diagnose further, correct again. 3rd failure: stop correcting in place and switch to a materially different approach -- this is the mandated action at the count, not something that resets the count. If that different approach also fails: isolate the failing part, finish independent work, and report the blocker explicitly rather than continuing to burn attempts. The count is per-task and carries across stage returns (e.g. a plan sent back to stage 2 and rejected again by stage 3 is failure #2 on the *same underlying task*, not a fresh count). **Task identity is the stage-1 requirement ID, not the stage-5 task-graph node** -- re-decomposing at stage 5 (splitting a failing task into smaller ones) does not create a new task identity and does not reset the count; the count is tracked against the originating requirement across any amount of re-decomposition. **What resets the count is not self-declarable by the orchestrator**, to close the obvious loophole (an orchestrator relabeling a rejected task as "new" to dodge escalation): the count resets only when stage 1 produces an objectively new requirements artifact for a different user-facing requirement -- confirmed by either the user, or the next goldfish review explicitly noting it's a different problem. That goldfish is still briefed by the same orchestrator that was just rejected (there's no avoiding that -- someone has to write the brief), so its "different problem" confirmation is a check on the *stated* difference, not an independent re-derivation from scratch; it is not a complete defense against a sufficiently motivated orchestrator, and this doc says so rather than implying otherwise. For a plan stuck at Gate 0 (stage 2/3) specifically, "switch approach" at failure 3 means: pick a materially different architecture alternative already listed in the design doc's own alternatives section, or escalate to the user for direction -- never resubmitting the same design doc with cosmetic wording changes. A stream that can't make progress does not block sibling streams (global "one blocker never halts unrelated work" rule).
