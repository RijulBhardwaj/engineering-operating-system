# Release Review Passes

Concrete dispatch content for `workflows/end-to-end-development/README.md`'s Review Council (stage 8) and infra/compliance validation (stage 9) -- these are the actual prompts/briefs each reviewer agent gets, not just a role name. Adapted 2026-11-24 from a community-shared "vibecoder" release-review workflow (r/vibecoding, u/spex, "Security and maintainability guide for vibecoders"), restructured into this harness's existing roles rather than copied as standalone prompts.

**Core discipline, the one rule that makes the rest work**: generate -> freeze -> review (each pass below) -> patch *only the approved findings* -> final release gate. Never let a reviewing pass also patch the code it's reviewing (same as this harness's existing no-self-approval rule), and never let a patch pass "improve while fixing" beyond what a specific approved finding calls for (same as `coding-standards.md`'s smallest-correct-change rule). A reviewer that finds and fixes in the same turn is the exact failure mode this file exists to stop.

## The passes

Each pass is a separate dispatch (fresh agent/subagent, no cross-contamination of findings unless named below), output as a findings table (ID, severity, file/function, issue, exploit/failure scenario, recommended fix, confidence) -- never "looks good" without evidence, per `agent-coordination.md`.

1. **Security audit pass** (`ecc:security-reviewer` / `security-engineer`, stage 8) -- OWASP ASVS-style: authn/authz flaws, broken access control, injection (SQL/command/template/LDAP/NoSQL/path traversal), insecure upload/download, SSRF/XXE/deserialization/prototype pollution, secret exposure, unsafe env-var handling, insecure CORS/cookies/sessions/JWT/OAuth/API keys, missing input validation/output encoding, crypto mistakes, sensitive-data logging, leaky error handling, dependency/supply-chain risk, dangerous defaults, insecure Docker/CI/CD assumptions. Explicitly: do not patch yet.
2. **Adversarial security pass** (a *different* fresh reviewer, not the same session/agent as pass 1, per Gate 0's own goldfish principle) -- assume the app is exposed to the internet; hunt specifically for what pass 1 structurally tends to miss: unstated security assumptions, unmodeled trust boundaries, user input reaching sensitive sinks, privilege escalation, IDOR/BOLA, race conditions, unsafe background jobs/queues/cron/webhooks/file processors, unsafe admin/debug routes, missing rate limits, missing audit logs, missing abuse-case handling. Output only *new* findings plus previously-underrated ones -- no re-listing pass 1's findings.
3. **Dependency/supply-chain pass** (maps to this harness's existing dependency-audit tooling -- `npm audit`/`pip-audit` give the mechanical signal; this pass is the human-equivalent read of what those tools can't catch): unnecessary/abandoned/suspicious packages, typosquatting risk, broad install/postinstall scripts, missing lockfiles, dependency-confusion risk, unsafe CI secrets exposure, unpinned Docker images, missing SBOM/provenance, build steps fetching remote code, unsafe shell execution in scripts.
4. **Maintainability/future-dev pass** (`.claude/agents/code-reviewer.md`'s existing maintainability scope, made concrete) -- read as the maintainer inheriting this six months from now: unclear architecture, duplicated logic, hidden coupling, confusing names, oversized files/functions, missing comments where intent isn't obvious, stale/lying comments, missing error boundaries, fragile assumptions, scattered config, business logic mixed with UI/transport, unexplained security-sensitive code, places a future dev is likely to break security by accident. Do not optimize or rewrite for style alone.
5. **QA/abuse-case pass** (`qa-engineer`, feeds `ai-code-qa-gate.md` layers 2/3) -- design the actual tests: unit, integration, security regression, authz, validation, malformed-input, rate-limit/abuse, path-traversal, API contract, deploy smoke tests. Per test: name, purpose, files/functions covered, expected result, why it matters, whether it blocks release. Then name the minimum test set required before release -- not every test imaginable, the actual gate.
6. **Patch pass** (only after 1-5 produce findings and specific IDs are approved -- `quality-gatekeeper.md` or the user approves which): patch *only* the approved finding IDs. Preserve existing behavior unless a finding requires changing it. No feature removal. Smallest safe change per finding. Every security-sensitive fix gets a test. Update docs if setup/config/behavior changes. No new dependency unless justified. Keep a changelog of files touched.
7. **Final release gate** (`quality-gatekeeper.md`, feeding `architecture.md` Gate 6): known security findings, unresolved TODO/FIXME/HACK, secrets/test credentials, debug routes, verbose errors, missing env/install/run/test/rollback docs, missing monitoring notes, missing ownership notes, dependency/license risk, tests passing-and-documented, migration/setup risk. **Verdict, stated explicitly, one of exactly three**: `ship` / `ship with conditions` (name them) / `do not ship` (name the blockers). Never a vague "looks mergeable."

## Live walkthrough (the eighth pass -- not an LLM read of the diff, an actual run of the app)

Adopted per explicit user instruction ("include the live open the all and click through each as a part of the audit"). None of passes 1-7 touch the running application -- they all read code. This pass does not skip that gap:

1. Launch the app for real (`preview_start`, or the project's actual run command) -- not a mock, the thing that will ship.
2. Walk every reachable page/flow/state, cross-checked against `ui-ux-states.md`'s 44-state checklist for whichever states that surface actually has (empty/loading/error/success/validation/etc.) -- click through each one, don't just list them as reviewed.
3. At each state: screenshot or `read_page` to confirm it renders as designed, `read_console_messages` for JS errors, `read_network_requests` for failed/slow calls -- the same evidence-not-assurance standard as every other layer.
4. Anything pass 1-7 claimed ("input is validated," "error states are handled") gets spot-checked live here, not taken on the static read alone -- a reviewer reading code can miss what only shows up at runtime (a validation rule that exists in one file but not the endpoint that actually receives the request, for instance).
5. Findings here feed back into the same table format as passes 1-7 and the same approved-findings-only patch discipline in pass 6 -- this is not a separate, looser bar.

This pass is mandatory for anything with a UI before Gate 6 (`architecture.md`); a pure library/CLI/backend-only project with no UI surface skips it (nothing to click through) but still gets an equivalent live run (actual CLI invocation / actual API call) proving the thing works as shipped, not just as reviewed.

## Baseline checklist (ninth pass -- Zapier "vibe coding security" baseline)

Adopted 2026-11-24 per explicit user instruction, source: zapier.com/blog/vibe-coding-security (Zapier blog, "How to make sure your vibe-coded app is secure"). Folded in as a mandatory pre-flight checklist, not a separate review round -- these five items are concrete, narrow checks the passes above can miss if a project skips architecture.md's spec-driven step and jumps straight to code:

1. **Build securely from the start, not bolted on after.** Covered structurally by `architecture.md`'s spec-first/Gate-0 ordering -- flag any project where security requirements were written after implementation, not before.
2. **Security review loop exists** -- satisfied by this file's passes 1-2 plus the live walkthrough; a project with no review loop at all fails this item outright, independent of code quality.
3. **Database locked down with row-level security (RLS) or equivalent row/tenant-scoped access control** -- add as an explicit line item to the security audit pass (pass 1) and the database-reviewer persona's checklist whenever the project has multi-tenant or per-user data in a shared table/DB. Missing RLS on a table holding another user's data is a standalone CONFIRMED finding, not folded into generic "authz."
4. **Keys and secrets protected** -- already covered by `security.md`'s no-committed-secrets rule and this file's pass 1 secret-exposure check; this item exists here only to name it explicitly as part of the baseline, since it's the single most common vibe-coded-app leak per the source article.
5. **Access control: who can access what** -- same authz/IDOR scope as pass 1/2, named explicitly so a reviewer checks role/permission boundaries even on a project with no obvious "auth system" (a public app with an admin-only action still needs this).
6. **Sensitive logic kept off the user's device** -- add as an explicit check in the security audit pass and the live walkthrough: any pricing calculation, entitlement check, API key, or business rule that must not be user-tamperable must run server-side, never shipped to the client and trusted. Client-side-only validation of a security-relevant rule is a CONFIRMED finding.

Explicit honesty note carried over from the source: no app is 100% secure. This checklist narrows the attack surface; it is not a guarantee, and the Review Council's residual-risk statement (`workflows/end-to-end-development/README.md`) still applies on top of a clean pass here.

## Where this plugs into the existing pipeline

- Passes 1-5 + live walkthrough + baseline checklist = `workflows/end-to-end-development/README.md` stage 8 (Review Council) content, plus stage 9 for the supply-chain/infra-level parts.
- Pass 6 (patch) = back to stage 6 (implementation), evidence-tagged with the approved finding IDs, per the pipeline's own loop-back table.
- Pass 7 (final release gate) = `architecture.md` Gate 6 / `quality-gatekeeper.md`'s existing scope, now with the explicit ship/ship-with-conditions/do-not-ship verdict format.
- All of it sits behind the hard gate in `git-workflow.md`: a PR does not open until the mechanical layers (ai-code-qa-gate.md 1-3,5) pass locally; these passes are the human-equivalent layer-4 content that runs before merge, same ordering.
